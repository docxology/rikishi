# Finite alignment study

`rikishi.alignment` executes a versioned, source-bound finite experiment. Its
authority is [`alignment-study-v1.json`](../src/rikishi/data/alignment-study-v1.json).
That authority fixes source revisions and hashes, original workbook locators,
local sense decisions, complete formula selections, first-order logic (FOL) interpretation, resource
limits, competency polarities, random generator, model dimensions, candidate
laws, Decimal precision, tolerances and numerical boundary cases before execution.
A supplied study file must equal this supported packaged version. A new study
requires a separately versioned authority and implementation review.

### Dependency provenance revisions

The authority also pins exact dependency-input bytes. A release-only change to
Rikishi's editable version in `uv.lock` requires updating the dependency digest in
both this authority and the [shared-witness authority](../src/rikishi/data/fep-sumo-bridge-v1.json).
First prove that every other lock value and all scientific definitions, inputs,
source selections, resource budgets, expected polarities and tolerances are unchanged.
The scientific v1 identifiers and schema may then remain v1; the complete authority
content digests still change. This is a provenance revision, not a new study result.
Changes to the study definition require the separately reviewed version above.

Preserve old authorities, receipts and packets under their original identities.
Acquire a fresh portable-input bundle and execute new affected alignment and
shared-witness campaigns before rendering. Strict current replay must reject old
authority packets; never substitute new digests into old reports or relax equality
to make them appear current. Newly rendered figure footers and editions carry the
new report identities even when the mathematical inputs and observations agree.

## Interpretation and limits

The local extension distinguishes an abstract model/content instance beneath
`Proposition` from a physical execution beneath `Process`. It asserts
`abstractCounterpart(model, execution)` with abstract first argument and physical
second argument. These are locally authored modeling choices. They deliberately
distinguish the precedent's proposed `GenerativeModel` Process placement from
the content sense used here. They establish no physiological or biological fact.

The FOL carrier is nonempty and untyped. Class names are constants; `instance`
and `subclass` are binary predicates. The explicitly selected source edges are
`Process` beneath `Physical` and `Proposition` beneath `Abstract`. The kernel
adds instance inheritance, subclass transitivity, Physical/Abstract exclusion,
and the two selected argument types of `abstractCounterpart`. It does not import
partition exhaustiveness, universal Entity membership, general domain/range or
subrelation metatheory, other Suggested Upper Merged Ontology (SUMO) axioms,
higher-order constructs or Sigma caches. It does not provide general Standard
Upper Ontology Knowledge Interchange Format (SUO-KIF) translation or a full-SUMO consistency test.
There is no unique-name assumption; disjoint inhabited types force the two local
individuals to differ. Every selected source formula is retained in full with
its source path, start/end lines and hash. Kernel formulas and omissions are
visible study inputs, not hidden consequences attributed to SUMO.

The source report uses the existing portable SUMO-report method. Its complete Merge.kif
text is reparsed and its original derived observations are checked before the
study's additional citations are derived. Original XLSX bytes are retained and
the selected sheet and cells are reread from the workbook's Extensible Markup Language (XML), including blank
mapping cells and the sheet name's trailing space. The original access date is
retained. Source/sense coverage is explicitly limited to the listed rows.

The baseline must return `Satisfiable` before a campaign can be complete. Eight
query polarities test model/execution types and their excluded alternatives.
Additional controls alias the individuals, classify an empty class beneath both
disjoint branches, and inhabit that class. The empty class can be satisfiable;
its inhabited counterpart is inconsistent in this declared fragment. Unknown,
timeout, theorem, countermodel and contradictory-background outcomes remain
distinct. A countermodel is an outcome for the selected FOL premises and query.
It is not a countermodel of original SUMO.

## Numerical experiment

The matrix uses the authority's PCG64 seed, dimensions and integer-weight model
design. Each supplied model is evaluated with prior, uniform, exact-posterior
and posterior-mode candidates. The exact-posterior candidate is generated by
the independent Decimal reference. Matrix rows retain integer weights, actual
log inputs, linear candidate, reference values, kernel outputs, comparison
errors and predeclared tolerances. Counts are measured from produced rows.

The reference directly exponentiates the exact binary-float log inputs in an
80-digit Decimal context, sums positive joint masses, and computes posterior,
objective and Kullback-Leibler (KL) divergence using Decimal logarithms. It does not call `free_energy_log`.
Separate controls reverse states and rescale likelihoods by the authority's
factor, checking objective/evidence shifts and posterior invariance. Ordinary
and extreme cases use their respective fixed tolerances. The objective is
dimensionless, uses natural logarithms and is reported in nats; it is distinct
from expected or Helmholtz free energy and the source's complexity wording.

`None` in a log input denotes exact zero support. `None` in returned linear
evidence denotes positive evidence below the float range. Finite log evidence
and log posterior retain that distinction; `posterior_underflow_indices`
identifies positive posterior mass whose linear projection underflowed. Invalid
normalization, dimension, nonfinite values, impossible evidence and positive
candidate mass outside joint support are retained as rejection cases.

Arithmetic, normalization, logarithms, posterior update and free-energy laws are
not encoded in the FOL problem. The logical and numerical results therefore
remain separate. No SUMO-to-Lean interpretation or preservation theorem follows.

## Importable integration

```python
from pathlib import Path
from rikishi.alignment import (
    alignment_substitutions, load_study, run_alignment, validate_alignment_report,
)

root = Path.cwd()
report = run_alignment(
    root, root / "fresh-study-output", study=load_study(),
    workbook_path=Path("source-inputs/active-inference-sumo.xlsx"),
)
checked = validate_alignment_report(root / "fresh-study-output/alignment-report.json")
assert checked == report
substitutions = alignment_substitutions(checked)
```

`run_alignment(root, output, *, study=None, source_report=None, workbook_path=None, prover="e")`
requires a fresh repository-local directory with an existing parent. It checks
the local Knowledge Interchange Format (KIF) extension and pinned dependency/source-lock bytes before writing.
It delegates every native invocation to `runtime.prove`; `prover="v"` selects
the optional installed second family. A separate output directory is required
for every run. Preexisting output is refused, never overwritten. Failure leaves
available evidence in place. No network, source index rebuild or upstream
modification occurs.
With `source_report=None`, the runner calls `demonstrate_sumo` on the authority's
live source index after its source audit; it never reads a previous generated
report. A supplied `source_report` selects an explicit frozen input instead.

## Preparing inputs in a fresh checkout

The default workbook location supports this working checkout's retained
evidence. It is not distributed input data. No XLSX is packaged. The default
source report is newly generated from the audited live index, not historical
output. `study.source_report_path` records the historical saved-fixture location
for explicit reuse only; it is not consulted by the default runner.
For a fresh installed checkout, use explicit `workbook_path` and `source_report`
arguments as below; relative paths resolve against `root`. Keep these acquired
inputs and all outputs on mounted GitVault, source `scripts/env.sh`, and use the
locked Python 3.12 environment. Bootstrap the pinned SUMO source and native
provers using the existing runtime setup workflow first. The study refuses a
different SUMO revision or complete-file hash.

The following shell commands acquire the original workbook from the official
Uniform Resource Locator (URL) stored in the packaged authority, then verify the exact pinned Secure Hash
Algorithm 256-bit (SHA-256) fingerprint.
The fresh filename check prevents overwriting an existing input.

```bash
set -e
source scripts/env.sh
mkdir -p source-inputs
test ! -e source-inputs/active-inference-sumo.xlsx
workbook_url="$(uv run --locked --no-sync python -c 'from rikishi.alignment import load_study; print(load_study().workbook_url)')"
curl --fail --location --output source-inputs/active-inference-sumo.xlsx "$workbook_url"
uv run --locked --no-sync python -c 'from hashlib import sha256; from pathlib import Path; from rikishi.alignment import load_study; p=Path("source-inputs/active-inference-sumo.xlsx"); assert sha256(p.read_bytes()).hexdigest() == load_study().workbook_sha256; print("Pinned workbook SHA-256 matched")'
```

Save the following Python program in a new file in the checkout and execute it
with `uv run --locked --no-sync python <file>`. It builds a fresh source index,
uses the existing source-audit/portable-report method, and supplies both inputs
explicitly. Neither historical `output/` nor `.omo/` files are read. The existing
native bootstrap's `.rikishi/upstream/sumo` source must match the repository lock.

```python
from pathlib import Path
from rikishi.alignment import run_alignment
from rikishi.ontology import OntologyIndex
from rikishi.sumo_demonstrations import demonstrate_sumo

root = Path.cwd()
inputs = root / "source-inputs"
index = OntologyIndex(inputs / "sumo.sqlite")
index.build(root / ".rikishi/upstream/sumo")
source = demonstrate_sumo(index, root)
with (inputs / "source-report.json").open("x", encoding="utf-8") as stream:
    stream.write(source.model_dump_json(indent=2) + "\n")
report = run_alignment(
    root, root / "fresh-study-output",
    source_report=Path("source-inputs/source-report.json"),
    workbook_path=Path("source-inputs/active-inference-sumo.xlsx"),
)
print(report.summary.model_dump_json(indent=2))
```

The source report is a generated retained input, not an independently downloaded
claim of authenticity. The runner reparses it, requires the authority's exact
Merge.kif hash/revision/path, rereads the supplied original workbook cells, and
freezes both inputs into its output. The workbook override changes acquisition
location only; it cannot substitute an alternative or rehashed workbook. The
same `workbook_path` argument can point to an already acquired, trusted copy.

The result is a frozen `AlignmentReport` Pydantic model, serialized to
`alignment-report.json`. Its directory also contains `study.json`, the complete
`source-report.json`, original `workbook.xlsx`, `extension.kif`, retained lock
files under `bindings/`, generated `problems/<case-id>.p`, and complete native
captures under `captures/<case-id>/`. Each run row binds its problem bytes,
capture bytes, invocation ID, solver family/hash, observed status and expected
polarity. Captures preserve raw stdout/stderr and strict input receipts.

`report.summary` supplies measured logical matched/mismatched/unresolved counts,
the baseline satisfiability condition, numerical and extreme pass counts,
invalid-case rejection counts, and `campaign_complete`. The separate
`semantic_validation` field remains false. Completion means only that this
finite campaign met its declared conditions. It is not an alignment-validation
badge. `alignment_substitutions(report)` supplies these summary fields as
`ALIGNMENT_<FIELD_NAME>` strings for publication adapters; call it on a report
returned by the runner or portable validator.

`report.numerical.rows` is the visualization matrix. Each row includes
`dimension`, `model_index`, `candidate`, `input`, `prior_weights`,
`likelihood_weights`, `result`, `reference`, `max_reference_error`,
`permutation_max_error`, `rescaling_max_error`, `tolerance` and `passed`.
Boundary rows and invalid-input observations are separate collections.
Publication adapters should derive denominators and plotted results from these
collections and the validated summary instead of repeating study counts.

## Portable replay and trust

`validate_alignment_report(path, *, trusted_report_sha256=None)` needs the
retained directory and matching installed implementation/dependencies, but no
native executable, mutable upstream checkout or original source index. It
rederives complete source citations, workbook cells, all problem bytes,
numerical matrix/results and summary. It checks strict captures, their complete
campaign bindings, resource policy, status/exit agreement and polarity. It
rejects rehashed false source claims, results and polarities rather than trusting
their checksums as proof. Relocating the directory leaves original source and
invocation identities as historical strings; replay reads retained files only.

Creation uses the runtime's trusted live invocation checks against the installed
binary and exact problem bytes. Portable replay checks internal consistency of
saved solver evidence. It does not rerun the solver, authenticate historical
process execution, or independently verify the mathematical proof object. An
attacker replacing every mutually consistent capture and report needs a
separately trusted outer binding to be detected. Retain the final report SHA-256
outside the report's writable directory and supply it through
`trusted_report_sha256` when that stronger custody is required. The report binds
each complete capture, so this outer report binding also covers the saved
solver outputs through the capture receipts. The packaged source/study hashes
are themselves a trusted implementation input, not proof of Git authenticity.

Focused unit/inference tests use real files and real E/Vampire invocations.
Copied-fixture mutation tests cover source bytes and claims, workbook cells,
polarity, derived numbers, problem bytes, solver output, captures, resources,
exit codes, bindings and summary. Rehashed contradictory/unknown baseline
fixtures remain incomplete. These adversarial saved fixtures are labeled as
controls; they are never evidence of a live contradictory/unknown invocation.
Full repository and manuscript acceptance are separate integration work.
